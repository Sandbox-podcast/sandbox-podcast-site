# DD-0062 Sources News et file de traitement

Date : 2026-10-19. Liste fournie par Lou ; mise en œuvre décidée par l'agent sur délégation (PD-0003).

Complément du même jour : [DD-0063](dd-0063-stabilisation-des-classements-news-et-time-machine.md) décrit le modèle réellement exécuté, les corrections des sources et les durées bornées de collecte, génération et traduction. Le [rapport de stabilisation](../site/audit-stabilisation-2026-10-19.md) contient le dernier relevé et distingue la PR 94 fusionnée des correctifs complémentaires locaux.

Le registre contient les dix adresses précédentes et les 95 nouvelles adresses uniques de la liste. MiniMax et MiniMax Audio partagent leur source ; The Rundown AI était déjà présent. Les URL de référence ne gardent aucun paramètre UTM. Un blog et un changelog du même éditeur restent deux points de collecte distincts.

Chaque passage horaire consulte le registre complet, avec quatre requêtes simultanées au maximum. Le collecteur lit les articles, les publications de recherche et les entrées de changelog identifiables par une date et une véritable ancre publique. Il accepte les attributs HTML cités ou non cités, les types Article, BlogPosting, TechArticle et ScholarlyArticle, et plusieurs formats de date. Il ne remplace jamais une date absente par la date de collecte. Les URL externes ne sont suivies que si leur origine est explicitement inscrite pour cet éditeur. Aucun refus d'accès n'est contourné.

La migration additive 0017 crée news_candidates. Elle conserve les nouveautés détectées avant la rédaction. La collecte les transmet par lots bornés à 20 entrées et en octets UTF-8. Les résumés et traductions sont produits ensuite, par lots de cinq candidats éligibles, en commençant par les plus anciens. Le traitement enchaîne les lots dans un budget de 22 minutes, avec une marge pour terminer le dernier. La file conserve le reste pour les passages suivants. Une URL déjà publiée ou déjà enregistrée n'est pas ajoutée une deuxième fois. Les articles publiés s'ajoutent toujours à news_items, consultable par pagination selon DD-0061.

Un candidat rejeté par les contrôles est retenté après 24 heures, trois fois au maximum, puis reste enregistré avec le statut rejected. La migration additive 0018 ajoute une réservation de vingt minutes. La sélection verrouille les lignes pour éviter deux traitements concurrents ; seul le jeton courant peut confirmer le lot. Après une interruption, le candidat redevient éligible à l'expiration de la réservation. Le compteur persiste aussi les tentatives interrompues : après trois essais, la ligne reste disponible pour examen avec le statut rejected. Une publication confirmée en base est exclue de la reprise même si son accusé a été perdu. Les candidats de plus de quatorze jours ne bloquent pas les nouveaux ; les articles déjà publiés restent dans le fil historique. Aucune ligne de la file n'est supprimée par ce lot.

Le workflow conserve sa cadence horaire. Il enregistre les candidats avant l'installation des modèles et traite ensuite les lots éligibles dans le temps disponible. La collecte n'attend donc pas que les résumés précédents soient terminés pour conserver les nouveautés. GitHub peut retarder un démarrage. Un arriéré peut aussi retarder la publication d'une fiche : la cadence de collecte ne promet pas une publication sous 60 minutes.

La lecture réelle des 105 index obtient 97 réponses HTTP 200. La vérification du contenu récupère 263 fiches récentes provenant de 62 sources. Au total, 77 sources fournissent des données datées et huit autres sont en lecture partielle. Huit adresses répondent HTTP 403 ou 429 ; douze autres n'offrent pas encore de lien, de date ou d'ancre utilisable par le parseur. Les 263 candidats passent le schéma de source. Ce contrôle ne lance pas de modèle et ne publie rien. Le relevé par source est dans news-sources-2026-10-19.csv ; les HTML et extraits restent dans le dossier local ignoré par Git.

## Livraison

Appliquer 0017 et 0018 après sauvegarde et accord sur la base cible, puis déployer la version correspondante de l'application et du workflow. L'API expose la version 2 du protocole de file. Le collecteur la vérifie avant de lire les 105 sources : le nouveau workflow refuse de fonctionner contre une ancienne application. Les variables et le secret existants sont conservés. Avant d'activer ce volume en production, contrôler le temps CPU, les minutes GitHub disponibles et la capacité Postgres pour la file et ses extraits. Le lot n'autorise ni forfait payant ni hausse de quota. La rétention de la file reste à décider avant une accumulation durable de gros volumes.

La page News reste fermée tant qu'aucune fiche validée n'est publiée. Les candidats en attente ne l'ouvrent pas. Après livraison autorisée, vérifier un premier cycle réel et suivre la taille de la file, les rejets, les sources en échec et les délais de publication. La génération complète sur les nouvelles sources n'a pas été exécutée sur ce poste, où le modèle n'est pas installé.
